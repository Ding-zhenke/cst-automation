# Codex 对话独立 CST 持久会话设计

日期：2026-10-27。状态：用户已批准，已实施；验证边界见 docs/VALIDATION.md。

## 1. 已确认的需求

- 每个对话首次实际建模时自动创建一个独立 CST Design Environment。
- 后续建模、配置、求解与在线结果读取持续复用该环境。
- 对话中断、结束一轮回复或 MCP 断开均不关闭 CST；只有用户明确要求关闭才释放。
- 中断后先恢复现场，从已完成阶段继续，不默认复制工程或从头建模。
- 不同对话的环境、工程写入、任务记录和产物互不混用。

## 2. 当前实现与改动依据

- `cst_solver/__init__.py`：`setup()` 创建 DE；`setup.attach()` 未指定 PID 时使用
  `connect_to_any()`，随后取 `active_project()`。多会话模式必须禁止这种隐式目标选择。
- `tpc_service/backends/cst_backend.py`：求解时 `setup(path)`，finally 调用 close。
- `tpc_service/circuit.py`：默认 app_factory 创建环境，操作结束后关闭。
- `cst_mcp/runtime.py`：RunService 为 MCP 进程内单例，没有对话绑定。
- `tpc_service/service.py`：已有单 worker、request_id 去重与任务持久化；恢复时将旧
  queued/running 标记 interrupted，不等于恢复工程或识别仍在运行的 CST。
- `tpc_service/registry.py`：已有工程副本与归属概念，但注册表只存内存，副本按源文件
  basename 放置；不同来源的同名工程可能冲突。没有跨进程写入占用协议。

以上是源码观察，不证明当前用户遇到的每次重复建模都由这些入口引起。

## 3. Approaches：候选与建议

1. 每个 MCP 进程保存自己的 CST 句柄：改动少，但 MCP 退出后失去执行所有者，无法可靠
   判断旧调用是否还在运行，不足以承诺跨中断恢复。
2. 本机常驻会话管理器，每会话独立执行进程：MCP 仅作客户端；可独立保留队列、句柄及
   会话身份，适合用户要求。增加进程管理和本机 IPC，是本设计的建议方案。
3. 每个对话独立 Windows 用户或虚拟机：隔离更强，但许可证、桌面和部署成本较高，
   超出本次本机多对话建模范围。

用户已批准按方案 2 实施。实现采用持久注册表的管理器 facade 与每会话常驻 worker，
不额外维持全局管理器守护进程；队列采用本机原子 JSON 文件，OS 文件锁保护归属。

## 4. 架构和所有权

调用关系：对话 → MCP 客户端绑定 → 会话管理器 → 专属 worker 进程 → 专属 CST DE。

- 管理器仅负责会话路由、绑定、状态和 worker 生命周期，不直接持有 CST SDK 句柄。
- 一个会话对应一个独立 worker 进程、一个 SDK 执行线程和一个独立 DE。
- 同一会话所有 CST SDK 操作串行；不同会话可并行。单独的只读监测器只读进程/窗口
  信息，不从其他线程调用 SDK。
- worker 与管理器独立于单次聊天命令和 MCP 传输生命周期；MCP EOF 不触发关闭。
- 首次真实建模先分配会话并创建 DE；能力发现、讨论、预览和离线读文件不启动 CST。
- 一个会话可以注册多个相关工程，但每次操作必须明确 project_id；不以当前活动标签
  决定目标。默认工作工程在会话中记录，多工程时由客户端明确选择。
- 低层 `setup()`/`attach(pid=...)` 保留既有显式 Python 用法。持久模式使用新会话借用
  接口；一次操作结束仅归还借用，不关闭 DE。不得全局修改 close 的既有语义。
- 恢复 attach 得到的低层对象仍是“借用”语义；关闭由会话层验证持久归属后调用专用
  释放路径，不通过改写 `_attached` 冒充拥有者，不关闭外部手工环境。

## 5. 对话身份与路由

- 不假设 MCP 自动知道 Codex thread ID，也不把 MCP 连接 ID、cwd 或聊天标题当作对话 ID。
- 首次调用通过明确的 conversation binding 创建 session_id 和客户端绑定凭据；若宿主
  确实提供稳定 thread ID，则通过适配器校验后使用，否则使用生成的绑定文件。
- 绑定文件保存为工作区内每对话独立的绝对路径。创建结果返回恢复引用，后续工具显式
  携带 session_id 与绑定凭据。共享 MCP 进程中不得设置“最后使用的会话”全局默认值。
- 新对话默认创建新绑定；接管现有会话需用户明确要求恢复该会话，并验证原绑定。
  分叉对话默认不继承写权限；若要复制模型，创建新会话和独立副本。
- 找不到绑定或身份不匹配时返回明确错误及恢复入口，不扫描任意 DE 自动接入。
- 首版接入指引要求每个对话保留独立恢复引用，绑定文件不得使用工作区内唯一默认
  文件。没有可信宿主身份时，服务验证的是凭据与会话的对应关系，无法独立验证
  “调用确实来自某个聊天”；工具会话隔离与真实聊天身份认证必须分别说明。
- 绑定凭据只作为本机路由能力，不写入常规日志；它不构成同一 Windows 用户下对恶意
  进程的强安全隔离。本方案保证受管理工具的操作归属，不宣称桌面应用完全隔离。
- 增加仓库内使用说明：CST 操作统一走绑定接口，不临时写脚本调用无 PID attach 或
  直接创建另一套 DE。外部脚本只通过同一会话客户端提交。

## 6. 固定路径与持久记录

默认根目录建议为 `E:\Autocode\cst-automation\work\sessions`，部署时允许显式选择
另一个已授权根目录；执行时不依赖 cwd，不因启动失败搬家。

每个 `<session_id>` 下包含：

| 路径 | 内容 |
| --- | --- |
| session.json | schema_version、会话归属、绑定摘要、状态、worker 身份、DE 身份 |
| projects/<project_id>/ | 工作工程及同名结果目录；包含工程注册记录 |
| jobs/ | 请求指纹、request_id、job_id、状态、执行前意图和完成回执 |
| checkpoints/ | 分阶段输入摘要、保存记录、readback 证据及完成状态 |
| artifacts/、logs/ | 本会话的预览、诊断、图表及审计 |

- 身份记录包括 PID、进程启动时间、可执行路径和 SDK 目标；PID 单独不能防止复用。
- 工程记录包括 source_path、执行路径、project_id、保存版本与会话归属；首次导入按
  工程对复制，恢复时复用已有副本，不重复调用 copy_project。
- 真实路径规范化并检查 junction/symlink；不同会话不能持有同一实际工程的写入租约。
  源工程相同时默认各自复制；就地编辑须显式选择，且同时只允许一个受管理写入者。
- 原子写入记录；使用 OS 锁与所有者实例标识保证一个 session_id 只有一个 worker
  执行者。心跳仅用于诊断，失去心跳不授权启动第二个写入者。
- `.cst` 与结果目录必须在 CST 空闲并确认保存后制作检查点；不边求解边复制活动结果。
- 绑定凭据与公共状态分开存储，限制为当前用户可读；work 保持忽略，不发布工程数据。

## 7. 生命周期

会话状态与任务状态独立记录，避免把“客户端停止等待”映射为任务失败。

| 事件 | 处理 |
| --- | --- |
| 首次建模 | 取得绑定、创建专属 worker/DE、记录身份，再按已审阅参数执行 |
| 后续操作 | 验证绑定、租约、DE 和工程身份，在原 worker 排队 |
| 回复结束、用户停止当前回复、MCP 断线 | 断开客户端等待；已有后台调用继续，不关闭 DE |
| 任务完成或失败 | 保存回执和现场；DE 保留。失败不触发整模重建 |
| 用户要求关闭本会话 | 拒绝新写入，处理当前任务，保存成功后仅关闭该会话 DE |
| 用户手工关闭 DE、崩溃或系统重启 | 标为 lost，按恢复规则处理；不能保证旧进程永存 |
| 用户要求关闭后再次建模 | 明确创建新一代 DE，复用保留工程；不暗中恢复已关闭进程 |

关闭时先将 close_requested 持久化，拒绝新写入；此前已接收的队列任务按顺序完成，
然后保存并关闭，不强杀。关闭回执丢失时按原 request_id 查询；不重复关闭或自动重开。
若用户明确
要求停止求解，使用经验证的停止路径；缺少支持则报告仍在运行。保存或关闭失败保留
closing_failed 状态与进程信息，不声称已关闭。没有自动空闲回收或隐式超时关闭。

## 8. 中断恢复和防重复

### 8.1 恢复顺序

1. 读取绑定、会话、工程和任务记录，确认没有其他有效执行所有者。
2. 原 worker 存活：重新连接并获取快照；running 任务继续等待，不重提。
3. worker 已退出但 DE 存活：验证 DE 完整身份后精确 attach；先识别是否仍有求解、
   弹窗或未完成 SDK 操作，再决定是否接受写入。不能因 worker 消失就假设 CST 空闲。
4. DE 也已退出：确认丢失后创建新一代 DE，打开最后确认保存的原工作工程，核对
   检查点；不从源工程重新复制。无保存工程时说明可恢复边界，不假装已有几何。
5. 无法判断操作是否完成：进入 needs_reconcile，仅允许诊断/读取；核对历史块、对象、
   参数、消息和运行证据。缺少可靠读回的非幂等操作不自动重放，返回具体待处理项。

### 8.2 去重与检查点

- DE 创建本身也是持久操作：先写 launch_intent，在 SDK 执行线程启动后记录完整
  进程身份，再转为 ready。若在启动后、身份记录前 worker 崩溃，进入 needs_reconcile，
  核对本次启动痕迹与进程归属；身份不明确时禁止自动再创建第二个环境。
- `(session_id, request_id)` 为请求唯一键；相同键相同内容返回原任务，不同内容拒绝。
  去重记录在首次副作用之前持久化。提交回执丢失时客户端仍使用原 request_id 查询。
- 分阶段 operation_id、输入摘要和完成回执用于续做；用户后续确实要再执行同样操作
  时分配新 operation_id，不用参数哈希永久禁止重复操作。
- 检查点区分 intent_written、applied_unconfirmed、saved、readback_verified。
  保存成功和几何确认成功分别记录。只有证据足够才跳过对应阶段。
- 相同模型计划恢复时保留原阶段 ID；参数改变时失效受影响阶段及依赖阶段，不重跑
  无关阶段。已完成阶段的现场与记录不一致时先报告差异，不自动覆盖人工修改。
- 不承诺 SDK 崩溃窗口里的任意命令 exactly-once。采取“记录意图、核对后继续”，
  无法确定时停在具体阶段；该限制是避免重复建模所必需的规则。
- 求解去重单独核对 run identity 和实际完成证据，不以存在结果目录或 FFT 文件认定
  本次求解成功。旧 JobStore 恢复不能直接将 persistent 模式的存活任务改成 interrupted。

## 9. 拟新增接口与兼容策略

以下是待实现的协议建议，不是当前可调用工具：

| 操作 | 语义 |
| --- | --- |
| ensure_session(binding, request_id) | 幂等建立或恢复绑定；该调用自身不启动 DE |
| session_status(session_id, credential) | 返回会话、工程、在途任务及恢复状态 |
| resume_session(session_id, credential) | 核对现场后恢复路由，不自动重放不确定操作 |
| close_session(session_id, credential, request_id, save=True) | 显式持久关闭请求 |
| 现有 build/solve/study/read 调用增加会话上下文 | 绑定目标并复用 worker/DE |

- 管理器必须校验调用者绑定，不仅依赖模型填写 session_id；响应带 session_id、
  project_id、job_id、environment_generation 和验证等级，便于核对。
- 现有稳定 RunService API 仍支持旧的临时模式；新增显式 persistent 模式。Codex
  集成切到持久模式，不能混用两种后端操作同一活动工程。
- 在修改跨包协议前先更新 `docs/PUBLIC_API.md`，再同步显式 handler/MCP 注册。
- 通用 handler 通过公开 session execution context 借用 app；不能在返回 JSON 放
  SDK 句柄。场路与领域扩展均改走该上下文，不各自 setup/close。
- close_project 仅处理工程；close_session 才释放 DE。若仍有本工程任务，拒绝立即关闭。
- 不改全局 Python、相邻仓库或用户全局 MCP 配置；先提供本仓库启动与接入说明。

## 10. 沙箱、启动和资源

- Codex 沙箱保留。IPC、启动器和会话目录遵守当前权限边界，不设计绕过权限的通道。
- 首次部署确定固定解释器、安装路径、会话根目录和受约束的本机 IPC；推荐 Windows
  文件队列放在当前用户信任的 work 根目录，不开放网络入口；协议仅允许显式会话
  操作，不提供任意 Python/shell 方法。history 的 VBA 属于受信任建模代码。
- 常驻启动器只在允许的用户权限与进程环境中启动；若沙箱限制进程寿命或 IPC，返回
  具体失败阶段与可审阅启动方式，不自动探索 explorer/计划任务等旁路。
- 管理器和 worker 必须实测脱离 MCP 命令生命周期；若宿主环境不支持，应报告该项
  尚未满足，不能把脚本已启动当成长驻保证。
- Python 和 SDK 配置可共享；可变工作文件、队列及 CST 句柄不共享。代码版本和配置
  指纹记录在会话中，升级不替换活跃 worker 的代码；新版本在下次受控启动生效。
- DE 许可不足时报告创建失败，绝不退回 connect_to_any 借用别的会话。求解并发按许可
  与计算资源另行限制；排队不改变会话归属、不关闭闲置 DE。

## 11. 实现范围、顺序与验收

建议分两段交付：先会话绑定、专属 worker/DE、统一借用、显式关闭；再持久恢复、
分阶段检查点与现场核对。第一段不能对外宣称完整中断恢复已完成。

实施计划的首项必须验证进程独立存活、精确重连以及 SDK 繁忙状态识别的可行性，
再建设协议和业务改动；worker 初始化和所有后续 SDK 调用均在同一专属执行线程。

离线验证重点：双绑定不串路由、同名工程不冲突、单会话串行/跨会话独立、并发创建
只产生一个 worker、请求重发去重、MCP 断线不关闭、旧请求冲突、恢复不重放不确定
副作用、关闭失败不误报，以及旧临时模式兼容。使用仓库 .venv 和 work 内测试目录。

实机验收使用两个经审阅的最小测试工程，依次验证：

1. 两对话首次建模得到两个不同且可核对的 DE，分别修改参数并原生读回。
2. 同一对话第二次操作复用 PID/环境代次及原工程；手工切换活动标签不会改错工程。
3. 中断聊天/MCP 后，原 worker 与 DE 保留；恢复后已建对象数量和历史不重复。
4. 分别覆盖提交回执丢失、worker 退出但 DE 存活、DE 丢失、保存后回执丢失；无法
   读回的阶段应进入 needs_reconcile，不自动重跑。此类破坏性注入仅针对测试会话。
5. 关闭 A 保存并释放 A，B 仍可操作；运行任务期间关闭按约定等待。
6. 若要宣称运行中求解恢复，另做短求解及真实运行身份核对；几何测试不能替代。

几何预览仍按现有规则先审阅；真实弹窗读取标题、正文、按钮和所属 PID。验收逐项
记录到 `docs/VALIDATION.md`；设计、离线通过、DE 复用、原生读回、求解分别计证据。

## 12. 待审阅决策

需要用户审阅的是架构方案和默认行为；不是额外的权限申请。本设计建议默认采用
方案 2、固定 work/sessions 根目录、新对话新会话、明确关闭才释放、状态不确定时
先核对再续做。宿主 thread ID 是否可用、进程独立存活、SDK 重新连接与繁忙判断能力
属于实现前技术验证项，不将其当作已有保证。

## 13. 设计复核

独立只读复核认为可进入实施规划；已补充聊天身份保证边界、DE 启动回执丢失窗口、
关闭请求前已接受队列的完成规则，以及只分配绑定不启动 DE 的接口语义。复核没有
执行代码或实机实验，不提高任何运行验证等级。
